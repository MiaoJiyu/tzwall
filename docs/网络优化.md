# 公网上行流量优化方案（设计文档）

> 范围：仅网页端链路（EdgeOne → Nginx 10001 → 后端 10002 → COS/PG/Redis），不动小程序。

## 一、流量来源与峰值特征（现状基线）

**公网上行 = 服务器面向互联网发出的字节**，按量级排序：

| 来源 | 现状 | 特征 |
|---|---|---|
| **① 媒体代理（图片/视频）** | 绝对主力。`GET /api/images/:id`、`/api/videos/:id` 由后端从 COS 取流转发，**每一字节都经过服务器出口** | 图片默认开盲水印：每请求经 COS 数据万象按"用户名+IP+时间"生成，**字节逐请求不同 → 无法共享缓存**（`Cache-Control: private, max-age=300`）；视频 `public, max-age=1d, immutable` 但同样过服务器 |
| **② 前端静态资源** | `favicon.svg` **约 4.0 MB/次**、`app.png` 89KB、`donate.jpg` 119KB、QQ/微信图标 27KB+1KB；`dist/assets` 4.7MB（hash 名，30d 缓存） | favicon 体积异常，是新会话/刷新的固定成本 |
| **③ API JSON** | meta、列表、详情、评论、公告等 | 单次小（几 KB），但**未读角标 15s/用户轮询**，用户量上来后累积可观 |
| **④ 其他** | `index.html`（no-cache）、错误页 | 量小 |

**峰值特征**（校园墙场景）：午休/晚间/活动后突发；热点帖（图/视频）访问集中；移动端为主；校园 NAT 导致**大量用户共用一个出口 IP**（限流与缓存键设计必须考虑）。

## 二、优化目标

1. **主目标**：服务器公网上行流量下降 **≥70%**（媒体为第一目标），EdgeOne/COS 流量费用同步下降。
2. **可用性**：P95 首字节与当前持平或更优；高峰期不因缓存策略劣化；下架/删除类操作**感知时效 ≤5 分钟**。
3. **可追踪**：任何一次媒体访问都能回答"谁、何时、哪个资源、走哪条缓存路径、是否带水印、多少字节"。
4. **安全**：加密、访问控制、限流、异常检测**不弱于现状**。
5. **功能保留**：盲水印能力完整保留（精度可权衡，见"关键权衡"）。

## 三、约束条件

1. 盲水印必须保留（溯源/审核是硬需求）；对象存储 ACL 私有、不可公开枚举。
2. 仅网页端生效，**小程序代码与链路零改动**。
3. 服务器资源有限（约 2GB 内存，构建已需限压），不得引入重计算或重内存组件。
4. 不得削弱现有鉴权（图片签名链接、登录态、JWT）。
5. 维护模式（nginx 标志文件）与现有部署/构建流程保持可用。

## 四、可衡量效果指标（KPI）

| 指标 | 基线（待埋点确认） | 目标 |
|---|---|---|
| 服务器公网上行 GB/日 | 基线周统计 | **↓ ≥70%** |
| 媒体请求"边缘/源站缓存命中"占比 | ≈0（媒体基本不过边缘缓存） | **≥85%** |
| 盲水印 CI 调用次数/千次浏览 | 1000 | **≤100**（按用户+时间桶复用） |
| COS 外网下行（COS→服务器） | 与媒体量成正比 | ↓ ≥70%（改内网 + 源站盾） |
| 静态资源人均重复传输 | favicon 4MB/会话 | ↓ ≥95% |
| P95 首字节 / 错误率 | 当前值 | 不劣化 |
| 下架内容缓存残留时长 | — | ≤5 分钟 |
| 访问日志关键字段完整率 | 已有 17,696 条访问日志 | 100% |

## 五、优化设计（方向与机制）

### 5.1 流量分层：把媒体移出服务器路径
- **A 类 · 展示态（可公开长缓存）**：列表/详情/缩略图所用的媒体，由 **CDN/对象存储直出**（限时签名 URL），服务器只签发不转发字节；前端已有的**可见水印覆盖层**继续承担"观感水印"。
- **B 类 · 盲水印态（按用户变化）**：保留后端路径，但结果按"**用户 + 时间桶**"复用（见 5.3），浏览器 `private` 缓存；CDN 不透传缓存。
- **C 类 · 低频重路径**：下载、取证、原图查看、管理端预览 → 走后端盲水印（量小，可接受成本）。

### 5.2 缓存分层与键策略
| 层 | 缓存对象 | 键 | TTL | 失效 |
|---|---|---|---|---|
| 边缘（EdgeOne） | A 类媒体、`/assets/*`、静态图 | 签名 URL / hash 文件名 | 与签名有效期匹配（A 类） / 30d（assets） | 主动刷新 |
| Nginx 源站盾 | A 类媒体、静态图 | `media:<id>:<版本>` | 1–7 天 | `proxy_cache_purge` / 版本号 |
| 后端字节缓存 | A 类（无水印） | `img:<id>` | 配置化 | 下架即删 |
| 盲水印结果 | B 类 | `wm:<imgID>:<uid>:<小时桶>` | 桶时长 + 缓冲（≈70min） | 自然过期 |

键带**版本号**（审核/替换版本），使失效可批量、可预测。

### 5.3 盲水印复用（保留功能的核心手段）
- 水印文本降维：`用户名 + 小时时间桶`（去掉 IP 与秒级时间）→ 同用户同桶内多次浏览**共用一份水印字节**；
- 命中即零 CI 调用；未命中才生成并回填；
- 提取端（`/api/admin/watermark/extract`）沿用 `watermark/4` 文本提取，**溯源粒度从"请求级"变为"用户+小时级"**（明确权衡，需业务确认）；
- 仅网页端启用，小程序链路不变。

### 5.4 静态资源与 API 瘦身
- `favicon.svg` 4MB → 替换为轻量矢量/位图（**单项即可省掉可观的固定成本**）；
- 图片格式现代化（WebP/AVIF）与**尺寸分级**（缩略图/列表图/原图），按场景取最小满足尺寸；
- API：`meta`/公告/配置类加 **ETag/304**；未读轮询**自适应**（页面可见 30s、隐藏即停）；JSON 压缩（已有 gzip，建议增 Brotli）+ HTTP/2。

### 5.5 预热与失效
- **预热**：投稿审核通过 → 异步把媒体灌入"源站盾 + 边缘"；首页/热榜定时预热；
- **失效**：下架/删除 → 按 `media:<id>` 广播清除（边缘刷新 → nginx → 后端字节缓存 → Redis 水印桶），并记录失效审计。

## 六、可追踪性要求

1. **流量日志字段**（在现有 `access_logs` 基础上补齐）：请求 ID、用户/游客、IP、资源类型与 ID、**字节数**、**缓存状态**（边缘 HIT / 源站盾 HIT / 回源 MISS / 水印复用 HIT）、是否走盲水印、响应码、耗时。
2. **链路一致性**：`X-Request-Id` 贯穿 EdgeOne → nginx → 后端 → COS，任一条日志可拼出完整路径。
3. **审计记录**：缓存刷新、预热、签名异常、限流触发、下架传播等纳入 `audit_logs`（管理员操作已有，需扩展流量类事件）。
4. **双向溯源**：
   - 正向：一条访问 → 用户、资源、水印批次、缓存路径；
   - 反向：水印提取结果 → 用户 + 时间桶 → 该桶内的访问日志。
5. **保留周期**：访问日志按 `log_access_retention_days`；安全类事件（封禁、限流、扫描）长期保留。

## 七、安全防护要求

1. **传输加密**：全链路 HTTPS（含 EdgeOne→源站）、HSTS。
2. **访问控制**：A 类直出必须**限时签名 + 绑定用户**，防分享扩散；防盗链（Referer）；COS 对象私有；密钥最小权限。
3. **限流与配额**：沿用权限矩阵；媒体端点按 IP/用户增加字节配额（如单用户每小时媒体字节上限），超限降级到 C 类或拒绝。
4. **异常检测**：单 IP/用户字节数突增、热点资源异常集中、错误率/扫描行为（遍历资源 ID）→ 告警并自动封禁（已有 IP 封禁机制）。
5. **防遍历**：资源 ID 不可枚举（UUID/签名），CDN 侧校验签名。
6. **内容时效**：下架后缓存残留 ≤5 分钟（失效通道的时效要求）。
7. **隐私**：日志中 IP 可哈希化；敏感配置加密存储（现状已具备）。

## 八、关键权衡

| 权衡 | 说明 |
|---|---|
| **水印精度 vs 命中率** | 请求级 → 用户+小时级：命中率大幅上升，但溯源精度下降；建议业务确认后可接受 |
| **CDN 直出 vs 鉴权强度** | 直出即"可被分享"，需限时+绑用户+配额补偿 |
| **缓存时长 vs 下架时效** | 长缓存省流量，但必须有可靠的主动失效通道（否则违规内容残留） |
| **前端覆盖层 vs 后端盲水印** | 前端覆盖层省 100% 媒体流量，但只剩"可见"；本方案取"A 类前端覆盖层 + B/C 类后端盲水印"的混合 |
| **COS 内网 vs 源站盾** | 源站盾省 COS 外网下行，但占服务器磁盘（需容量与淘汰策略） |

## 九、建议推进顺序（优先级，非实施步骤）

**P0 测量基线**（日志补字节/缓存字段）→ **P1 立竿见影**（favicon 瘦身、格式与尺寸分级、ETag/304、轮询自适应）→ **P2 主干**（A 类媒体 CDN 直出 + nginx 源站盾 + 预热）→ **P3 水印桶缓存**（需业务确认精度权衡）→ **P4 可观测性与异常检测补齐**。

> 预期：P1 即可消除最明显的固定浪费（favicon 4MB/会话）；P2+P3 达成"上行 ↓≥70%"的主目标，同时保留完整的水印溯源与审计能力。需要的话，我可以把其中任一阶段展开为可执行的技术方案与改造点。
